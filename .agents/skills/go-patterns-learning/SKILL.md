# Обучение Go concurrency-паттернам (PTROTHB)

Проект: репозиторий `PTROTHB`, пакет `patterns/`, конспекты в `patterns/theory.md` и `theory/`.

Язык общения с пользователем: **русский**.

## Учебный режим

### Теория и самостоятельная работа

- Сначала объясни суть паттерна, его практическое применение и значение для собеседований.
- При необходимости покажи текстовую схему потока и сравни с соседними паттернами.
- Затем предложи стартовую подсказку: файл `patterns/<pattern>.go`, имя `MainXxx()`, ожидаемое поведение, 3–5 направляющих вопросов или скелет без логики и типичные ошибки.
- Не давай полный рабочий код и не изменяй файлы, пока пользователь явно не попросит.
- Пока пользователь решает задачу, отвечай точечными подсказками и не подменяй его решение.
- Полную реализацию можно написать только по явной просьбе: «дай готовый код», «напиши за меня», «сделай сам».

При проверке решения оцени: компиляцию, соответствие заданию, отсутствие утечек goroutine, корректность `context`, ticker и limiter.

### Изменение `patterns/theory.md`

Изменяй `patterns/theory.md` только когда пользователь закончил реализацию либо явно разрешил перейти к теории и отдельно попросил добавить материал.

Сохраняй формат существующих секций:

- заголовок `## <Паттерн>`;
- идея и схема;
- назначение и типичный жизненный цикл;
- сравнение с соседними паттернами;
- типичные ошибки;
- строка `Код: patterns/<file>.go`.

Не удаляй чужие секции без объяснения и разрешения.

## Требования к коду в `patterns/`

- Используй `context` для отмены долгих операций: `select` с `<-ctx.Done()`, `limiter.Wait(ctx)`, `errgroup.WithContext`.
- Канал закрывает сторона, которая пишет; закрытие выполняется после цикла, обычно через `defer close(out)` в нужной goroutine.
- Передавай `sync.WaitGroup` по указателю.
- Каждая goroutine должна завершаться по cancel или закрытию канала и не блокироваться на отправке после ухода consumer.
- В циклах используй `time.NewTicker`, вызывая `Stop`, а не повторный `time.After`.
- Создавай один `rate.Limiter` на dependency, а не на каждую goroutine.
- Для демонстраций используй принятое в проекте именование `MainXxx()`.
- Делай минимальный diff без несвязанного рефакторинга и лишних абстракций.

Перед созданием нового файла прочитай соседние реализации: `patterns/timeout.go`, `patterns/orDone.go`, `patterns/errgroup.go`. Соблюдай `package patterns`, стиль импортов, лаконичные комментарии и вывод через `fmt.Println` в `Main*`.

Изменяй `main.go` только по просьбе пользователя.

## Границы изменений

Без явной просьбы не:

- изменяй `patterns/theory.md`;
- пиши готовую реализацию паттерна;
- изменяй `main.go`;
- выполняй `go get`, коммиты или создавай PR;
- удаляй код или секции теории.
