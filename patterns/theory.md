# Concurrency-паттерны в Go

Опора: [Go Concurrency Patterns: Pipelines and cancellation](https://go.dev/blog/pipelines), [Go Concurrency Patterns (Rob Pike)](https://go.dev/talks/2012/concurrency.slide), пакеты `sync` / `context`.

Связано с: `theory/12` (горутины и каналы), `theory/13` (`sync` / atomic), `theory/11` (context).

---

## Общая теория

**Паттерн concurrency** — повторяемая схема организации горутин и каналов (иногда + `sync` / `context`), которая решает типовую задачу: ограничить параллелизм, разбить обработку на стадии, собрать результаты, корректно остановиться.

В Go редко «изобретают» синхронизацию с нуля на мьютексах. Чаще данные текут по каналам, а горутины — это стадии или воркеры вокруг этих потоков. Канал здесь и очередь, и точка синхронизации, и способ backpressure (если потребитель не успевает, отправитель блокируется).

Ключевые правила, общие почти для всех паттернов:

- **Кто пишет — тот и закрывает** канал. Закрытие из нескольких мест или закрытие читателем → panic / гонки.
- **Закрытый канал** — сигнал «данных больше не будет»; `for range` по нему завершается.
- **Не копируй** `sync.WaitGroup` / `Mutex` после первого использования — передавай указатель.
- **Отмена** (`context`, `done`-канал) нужна, чтобы горутины не утекали при раннем выходе.
- Конкурентность без лимита опасна: «горутина на задачу» легко упрётся в память, scheduler и внешние сервисы.

Паттерны ниже часто **комбинируют**. Например, worker pool ≈ fan-out + (опционально) fan-in; pipeline может внутри стадии делать fan-out.

## Список паттернов

От простых к более тяжёлым (по порядку изучения).  
★ — **обязательно** (ядро для собеса / практики). Без ★ — по желанию, когда встретится задача.

| #   | Паттерн                | ★   | Суть                                                    | Когда нужен                                      |
| --- | ---------------------- | --- | ------------------------------------------------------- | ------------------------------------------------ |
| 1   | **Generator**          | ★   | Функция запускает горутину и возвращает канал с данными | Лениво/асинхронно производить поток значений     |
| 2   | **Pipeline**           | ★   | Цепочка стадий: каждая читает из `in`, пишет в `out`    | Обработка как конвейер: parse → transform → save |
| 3   | **Fan-Out**            | ★   | Несколько горутин читают из **одного** канала           | Распараллелить одну стадию                       |
| 4   | **Fan-In (Merge)**     | ★   | Несколько каналов сливаются в один                      | Собрать результаты параллельных воркеров/стадий  |
| 5   | **Worker Pool**        | ★   | Фиксированное N воркеров читают задачи из одного канала | Много однотипных задач, нужен лимит параллелизма |
| 6   | **Semaphore**          |     | Буферизованный канал ёмкости N как слоты                | Ограничить параллелизм без явного пула воркеров  |
| 7   | **Timeout / Deadline** | ★   | `select` с `time.After` / `context.WithTimeout`         | Не ждать операцию вечно                          |
| 8   | **Or-Done / Done**     | ★   | Обёртка: читать из канала, пока не пришёл сигнал отмены | Безопасно останавливать чтение при cancel        |
| 9   | **errgroup**           | ★   | Группа горутин + первая ошибка + отмена context         | Параллельные задачи с общей ошибкой/отменой      |
| 10  | **Drop / Bounded**     |     | При полной очереди отбросить или не блокироваться       | Перегрузка: лучше потерять задачу, чем зависнуть |
| 11  | **Rate Limiting**      | ★   | Тикер / token bucket ограничивает частоту               | Не долбить API чаще N раз в секунду              |
| 12  | **Request–Reply**      |     | Запрос + канал ответа в сообщении                       | RPC-стиль между горутинами                       |
| 13  | **Tee**                |     | Один вход → два (или больше) одинаковых выхода          | Размножить поток (лог + обработка)               |
| 14  | **Or-Channel**         | ★   | Первый сигнал из нескольких `done`/`or` каналов         | «Завершись, как только сработает любой источник» |
| 15  | **Heartbeat**          |     | Периодический сигнал «я жив» по каналу                  | Детектить зависшие воркеры / долгие стадии       |
| 16  | **Publish–Subscribe**  |     | Издатель шлёт события многим подписчикам                | Рассылка уведомлений, event bus                  |
| 17  | **Bridge**             | ★   | Канал каналов «развернуть» в один плоский канал         | Динамические источники данных                    |

## Как читать карту

Сначала база из Tour / theory 12–13: горутины, каналы, `select`, `WaitGroup`, mutex.

Потом по таблице сверху вниз:

1. **Generator → Pipeline** — поток и стадии.
2. **Fan-Out → Fan-In** — раздать и собрать.
3. **Worker Pool / Semaphore** — явно ограничить параллелизм.
4. **Timeout / Done / errgroup** — отмена и ошибки без утечек.
5. Дальше (drop, rate limit, tee, bridge…) — по ситуации; на собесесах реже.

Worker Pool в списке после Fan-Out не потому что «сложнее синтаксисом», а потому что так яснее: pool — это осознанный **bounded** fan-out, а не отдельная магия.

## Generator

Идея: функция **асинхронно производит поток значений** и сразу возвращает канал для чтения. Caller не ждёт, пока всё сгенерируется — он получает «трубу» и забирает данные через `for range`.

```text
generator() → <-chan T → for v := range ch { … }
```

Generator — **источник** в pipeline и часто в fan-out / worker pool (канал задач). Твой `gen` в `pipeline.go` и `fanGen` — уже generator, просто без отдельного имени паттерна.

### Чем не является

Канал — не массив и не слайс. Это типизированная точка обмена между горутинами с синхронизацией внутри runtime. Generator не отдаёт слайс «всё сразу», а **поток** по мере чтения.

### Типичный цикл жизни

1. Создать `out := make(chan T)`.
2. В **одной** горутине `go func() { … }()`:

- цикл генерации;
- `out <- value` для каждого значения;
- `close(out)` **после цикла** (один раз).

3. Сразу `return out` (часто тип `<-chan T` — только чтение снаружи).

Consumer: `for v := range generator() { … }`.

### Варианты

| Вид             | Поведение                                                              |
| --------------- | ---------------------------------------------------------------------- |
| **Конечный**    | N значений → `close`. Аргументы: `nums ...int`, обход слайса           |
| **Бесконечный** | цикл без конца (счётчик, тикер) → нужна **отмена** (`context`, `done`) |

### Важные детали

- `out <-` **не в текущей** горутине до `return` — на небуферизованном канале deadlock.
- **Одна** горутина на генерацию, не `go` на каждое значение в цикле снаружи.
- `close` внутри цикла → panic на следующей отправке / повторном `close`.
- Бесконечный generator без cancel → утечка горутины, если consumer перестал читать.

Код: `patterns/generator.go`.

## Pipeline

Идея: обработка как **конвейер** из стадий. Данные идут по цепочке каналов:

```text
gen → square → somePrint → потребитель (range)
```

Каждая стадия — функция вида «взял входной канал → вернул выходной». Внутри она запускает горутину: читает вход (`for range`), делает свою работу, пишет в свой `out`, затем **закрывает** `out`. Снаружи сразу возвращает канал, не дожидаясь окончания работы.

Отличие от worker pool: там много **одинаковых** воркеров на одном типе задач. В pipeline стадии **разные по смыслу** (сгенерировать → преобразовать → залогировать / сохранить).

Типичный цикл жизни стадии:

1. Создать свой `out`.
2. В `go func()` читать вход до закрытия.
3. Писать результаты в `out`.
4. После цикла — `close(out)` (один раз, **после** цикла, не внутри).
5. Сразу `return out`.

Источник первой стадии — **Generator** (см. выше): параметров-канала нет, функция сама кладёт значения в `out` и закрывает его.

Сборка конвейера — вложенный вызов:

```text
for v := range stageN(...stage2(stage1(gen(...)))) {
    // забрать итог
}
```

Важные детали:

- **Кто пишет — тот закрывает** свой выход. Входная стадия чужой канал не закрывает.
- У **слайса** `for i := range s` даёт индексы; значения — `for _, v := range s`. У **канала** одна переменная — это уже значение.
- `close` внутри `for` после первого элемента → panic на втором. `close` — после цикла.
- Расширения (не база): fan-out/fan-in внутри стадии, `context` для отмены, возврат `<-chan T` вместо двунаправленного `chan T`.

Код: `patterns/pipeline.go`.

## Fan-Out

Идея: **раздать** одну очередь задач на несколько горутин («веером»). Несколько исполнителей читают из **одного** канала, пока он не закрыт. Каждое значение забирает ровно один читатель — канал сам выступает раздатчиком.

```text
          ┌─ worker 1
jobs ────►├─ worker 2
          └─ worker N
```

Зачем: ускорить одну стадию (CPU или I/O), задав параллелизм числом воркеров N.

### Fan-Out и Worker Pool

Базовый код часто **похож**: N горутин + `for range` по одному каналу. Это нормально.

|          | Fan-Out                                                                     | Worker Pool                                           |
| -------- | --------------------------------------------------------------------------- | ----------------------------------------------------- |
| Уровень  | приём / идея раздачи                                                        | конкретная архитектура                                |
| Акцент   | распараллелить работу                                                       | **ограничить** параллелизм, держать фиксированный пул |
| Варианты | N читателей одного канала; `go` на каждую задачу; N копий стадии в pipeline | обычно долгоживущие воркеры + очередь                 |

Worker pool — частый способ сделать **bounded** fan-out. Fan-out шире: в pipeline это «несколько копий `square` на одном `in`»; бывает и unbounded (`go` на каждый элемент) — опасно без лимита.

### Типичный цикл жизни

1. Источник кладёт задачи в канал и **закрывает** его (в своей горутине).
2. Запустить N одинаковых воркеров: всем передать **один и тот же** канал.
3. Воркер: `for job := range jobs { … }`, затем сигнал завершения (`WaitGroup.Done`).
4. Дождаться всех воркеров (`wg.Wait()`).

Если у каждого воркера **свой** выходной канал — собрать их через **Fan-In** (см. ниже). Если все пишут в один общий `results` — закрыть его один раз после `wg.Wait()` (часто в отдельной goroutine).

### Важные детали

- В `fanOut` нельзя делать `for v := range jobs { go worker(v) }` в смысле «на каждое значение новый воркер с каналом» — воркерам нужен сам канал задач, а N задаётся отдельным циклом `for i := 0; i < N; i++ { go worker(jobs) }`.
- `Done` вызывает воркер в конце работы, не тот, кто сделал `go` сразу после старта.
- Порядок обработки/печати не гарантирован.
- Источник с синхронным `ch <-` до старта читателей на небуферизованном канале → deadlock; отправка в `go func`, как у generator/pipeline.

Код: `patterns/fan-out.go`.

## Fan-In (Merge)

Идея: **собрать** несколько входных каналов в **один** выходной. Зеркало fan-out: там раздача, здесь слияние.

```text
worker 1 ──► out1 ──┐
worker 2 ──► out2 ──┼──► merge (fanIn) ──► один канал ──► consumer
worker 3 ──► out3 ──┘
```

Зачем: после fan-out или параллельных стадий pipeline consumer хочет **один** поток данных, а не читать N каналов вручную.

Типичная цепочка:

```text
Generator → Fan-Out → Fan-In → range / save
```

### Типичный цикл жизни (`merge` / `fanIn`)

1. Создать общий `out`.
2. Для каждого входного канала — горутина: `for v := range in { out <- v }`, в конце `wg.Done()`.
3. В **отдельной** горутине: `wg.Wait(); close(out)` — закрыть только когда все копировщики закончили.
4. Сразу `return out` — caller читает через `for range`.

`close(out)` выполняется **строго после** `Wait`: пока хотя бы один копировщик может писать, закрывать нельзя → panic.

### Почему `Wait` + `close` в отдельной goroutine

`return out` должен произойти **сразу**, иначе caller не начнёт читать. Если вызвать `wg.Wait()` до `return` на небуферизованном канале, копировщики блокируются на `out <-`, пока нет читателя → deadlock.

Отдельная goroutine с `Wait` + `close` не блокирует возврат канала, но гарантирует корректное закрытие после слияния.

### Fan-In vs общий `results` у воркеров

|                | Все пишут в один `results` | Fan-In (N каналов → merge)               |
| -------------- | -------------------------- | ---------------------------------------- |
| Выход воркеров | один канал                 | у каждого свой `out`                     |
| Закрытие       | после `Wait` один раз      | merge закрывает объединённый             |
| Когда          | простой pool               | несколько источников, pipeline + fan-out |

Оба собирают в одно; fan-in явно называет паттерн **merge**.

### Важные детали

- Цикл по слайсу каналов: `for _, ch := range chans`, не `for ch := range chans` (индексы, не каналы).
- В `go func()` внутри цикла канал передавать **аргументом** `go func(c <-chan int) { … }(ch)` — иначе все goroutine прочитают последний канал из замыкания.
- Порядок значений в merged-потоке **не гарантирован**.
- Число элементов сохраняется: сумма по всем входам = сколько получит consumer (если никто не дропает).

Код: `patterns/fan-in.go`.

## Worker Pool

Идея: не `go` на каждую задачу, а **N постоянных воркеров** + канал задач.

Типичный цикл жизни:

1. Создать `jobs` (и опционально `results`).
2. Запустить N воркеров (`go worker(...)`).
3. Отправить задачи, **закрыть** `jobs`.
4. Дождаться воркеров (`WaitGroup` по указателю).
5. При наличии `results` — закрыть его после воркеров и забрать итог.

Код: `patterns/workerPool.go`.

## Timeout / Deadline

Идея: **не ждать операцию бесконечно**. Если работа не уложилась в срок — прервать ожидание и выйти (обычно с `context.DeadlineExceeded`).

```text
caller: select { результат из worker | <-ctx.Done() }
worker: select { долгая работа | <-ctx.Done() }
```

Зачем: HTTP/БД/API, pipeline, goroutine — без лимита caller или worker могут висеть и утекать. Подробнее про context: `theory/11`.

### WithTimeout vs WithDeadline

|         | `WithTimeout`                | `WithDeadline`                         |
| ------- | ---------------------------- | -------------------------------------- |
| Задаёшь | duration (`3 * time.Second`) | момент времени (`time.Now().Add(...)`) |
| Внутри  | deadline = now + duration    | явная точка «до когда»                 |
| Когда   | «не дольше N»                | «до 18:00», SLA до времени             |

Оба закрывают `ctx.Done()` по истечении срока. После создания — `defer cancel()` всегда.

### Типичный цикл жизни

1. `ctx, cancel := context.WithTimeout(...)` или `WithDeadline(...)`.
2. Worker в goroutine: `select` между работой (`time.After` / I/O) и `<-ctx.Done()`.
3. При успехе — send в канал результата через вложенный `select` (с `<-ctx.Done()`, если caller уже ушёл).
4. Caller: `select { msg := <-res | <-ctx.Done() }`.
5. При timeout вернуть понятную ошибку: `ctx.Err()`.

### `select` и `<-`

`case <-time.After(7 * time.Second):` — **receive** из канала таймера (ждём событие «прошло время»).  
`case <-ctx.Done():` — receive из канала отмены.  
`case msg := <-res:` — дождаться результата worker’а, не «проверка пустоты» канала.

В `select` только **операции с каналами** (send/receive) + `default`.

### Отмена worker’а

Caller вышел по timeout → worker тоже должен слушать **тот же** `ctx`.  
`time.Sleep` не прерывается — оборачивают в `select` с `time.After` и `ctx.Done()`.  
При отмене **не слать** в `res`, если caller уже не ждёт — иначе goroutine зависнет на send.

### Важные детали

- Таймаут задаёт **caller** (верхний уровень), не worker.
- `WithTimeout` предпочтительнее голого `time.After` в сервисах — один ctx на весь запрос.
- `time.After` в **цикле** создаёт новый таймер каждый раз — в hot loop лучше `NewTimer` или context.
- I/O без context (`http.Get` без `NewRequestWithContext`) — внешний timeout не отменит запрос внутри.

Связь: **Or-Done** — обобщение «читать канал, пока не отменили»; timeout — частный случай (см. ниже).

Код: `patterns/timeout.go`.

## Or-Done / Done

Идея: **безопасно читать из канала**, пока не пришёл сигнал отмены. Если consumer ушёл (timeout, cancel), стадия pipeline не должна вечно блокироваться на `<-in`.

```text
in ──► orDone(ctx, in) ──► out ──► for range (main)
              ▲
         ctx.Done()
```

**Done** — канал «хватит, выходим»: `ctx.Done()` или отдельный `done chan struct{}` (закрывает тот, кто отменяет).

**Or-Done** — обёртка: на вход `ctx` + канал данных, на выход новый канал; внутри goroutine пересылает значения, но **прерывается** по cancel или когда `in` закрыт.

Timeout — частный случай: done = `ctx.Done()` после `WithTimeout`.

### Зачем

`for v := range in` не знает об отмене. Без orDone goroutine зависнет на read/send, если upstream ещё шлёт, а downstream уже ушёл. В [pipeline с cancel](https://go.dev/blog/pipelines) каждая стадия должна слушать done.

### Типичный цикл жизни (`orDone`)

1. `out := make(chan T)`.
2. `go func() { defer close(out); for { select { ... } } }()`.
3. Внешний `select`:

- `v, ok := <-in` — если `!ok`, выход (upstream закончил);
- `<-ctx.Done()` — выход (отмена).

4. Внутренний `select` при send: `out <- v` **или** `<-ctx.Done()` — не зависнуть, если consumer уже ушёл.
5. Сразу `return out`.

Consumer: `for v := range orDone(ctx, gen()) { ... }` — при cancel `out` закроется, цикл завершится.

### `select`, не `switch`

`select` ждёт **готовность каналов** (read/send/cancel). `switch` ветвится по **уже известному** значению. Or-Done нужен именно `select`: параллельно ждать `in` и `ctx.Done()`.

### Проверка `ok`

```go
v, ok := <-in
if !ok { return }  // in закрыт, данных больше не будет
```

`ok == false` — канал закрыт и опустошён. Без проверки не отличить «пришёл ноль» от «поток кончился».

### Done-канал vs context

|        | `done chan struct{}` | `ctx.Done()`                   |
| ------ | -------------------- | ------------------------------ |
| Отмена | `close(done)`        | `cancel()` / timeout           |
| Где    | локальный pipeline   | запрос, deadline, дерево отмен |

### Важные детали

- `defer close(out)` — **внутри** goroutine orDone, не снаружи (иначе `out` закроется до первой отправки).
- `defer close(out)` — в **начале** goroutine, не после `for` (иначе недостижим).
- Generator без ctx после cancel может ещё блокироваться на send — в проде upstream тоже слушает `ctx`.
- Or-Done ≠ fan-in: один вход → один выход с отменой.

Код: `patterns/orDone.go`.

## errgroup

Идея: **несколько горутин как одна операция** — дождаться всех, вернуть **первую ошибку**, при `WithContext` **отменить остальных**.

```text
                    g.Go(task1)
                    g.Go(task2)  ──► g.Wait() ──► err (первая) или nil
ctx (WithContext) ─► g.Go(task3)
                    ▲
              cancel при первой ошибке
```

Пакет: `[golang.org/x/sync/errgroup](https://pkg.go.dev/golang.org/x/sync/errgroup)` (не stdlib, но де-факто стандарт для сервисов).

### Зачем

`WaitGroup` ждёт завершения, но **не собирает ошибки**. Ручной код «N goroutine + chan error + cancel» быстро разрастается. errgroup даёт:

- `Go(f)` — запустить задачу;
- `Wait()` — блок до конца всех, вернуть **первую** ненулевую ошибку;
- `WithContext(parent)` — при первой ошибке вызывается `cancel()`, sibling-горутины могут выйти по `ctx.Done()`.

На собесе: «параллельно дернуть 5 API / прочитать 3 шарда БД — одна ошибка отменяет остальное и поднимается наверх».

### Базовый API

```go
var g errgroup.Group

g.Go(func() error {
    // ...
    return nil // или fmt.Errorf("...")
})

if err := g.Wait(); err != nil {
    // первая ошибка из Go(...)
}
```

`Group` **без** context: ошибка одной goroutine **не отменяет** другие — они доработают сами. Отмена только с `WithContext`.

### WithContext — главный режим

```go
g, ctx := errgroup.WithContext(context.Background())

g.Go(func() error {
    select {
    case <-time.After(2 * time.Second):
        return nil
    case <-ctx.Done():
        return ctx.Err()
    }
})

g.Go(func() error {
    time.Sleep(500 * time.Millisecond)
    return errors.New("упало")
})

err := g.Wait() // err != nil, ctx уже отменён
```

Правило для задач: **слушать** `ctx` (sleep, HTTP, DB, цикл) — иначе после первой ошибки goroutine «висит» до конца работы.

### errgroup vs соседи

|                    | WaitGroup | errgroup.Group | errgroup.WithContext |
| ------------------ | --------- | -------------- | -------------------- |
| Ждёт всех          | да        | да             | да                   |
| Первая ошибка      | нет       | да             | да                   |
| Cancel siblings    | нет       | нет            | да                   |
| Лимит параллелизма | вручную   | `SetLimit(n)`  | `SetLimit(n)`        |

Worker pool — **фиксированные воркеры** на очереди. errgroup — **один «залп»** задач на операцию (запрос, batch). Часто вместе: `SetLimit(10)` ≈ «не больше 10 одновременно».

### SetLimit

```go
g, ctx := errgroup.WithContext(ctx)
g.SetLimit(3) // не более 3 активных Go одновременно
```

С Go 1.20+. Семaphore-подобное ограничение без своего канала.

### Типичные ошибки

- Захватить **родительский** `ctx` в `Go`, а не тот, что вернул `WithContext` — отмена не дойдёт.
- Игнорировать `ctx` в долгих задачах — утечка goroutine после `Wait`.
- Вызывать `Go` **после** `Wait` — panic.
- Ждать, что errgroup закроет каналы — **нет**, это только sync + error + cancel.
- Путать с fan-in: errgroup не сливает потоки данных, только жизненный цикл goroutine.

Код: `patterns/errgroup.go`.

## Rate Limiting

Идея: **ограничить частоту** операций — не чаще N раз в секунду к одной dependency (API, БД, очередь). Реализация — **token bucket**: в «ведре» до `burst` токенов, пополнение с заданной скоростью.

```text
goroutine 1 ──┐
goroutine 2 ──┼──► один *rate.Limiter ──► Wait(ctx) ──► HTTP / DB / …
goroutine N ──┘         ▲
                  rate.Every(d) + burst
```

Пакет: `[golang.org/x/time/rate](https://pkg.go.dev/golang.org/x/time/rate)` (модуль `golang.org/x/time`, не stdlib).

### Зачем

Без лимита N goroutine могут **одновременно** ударить по API в одну миллисекунду → 429, бан, перегруз dependency. Rate limit **растягивает** вызовы во времени. На собесе: «как не долбить внешний сервис»; отличие от worker pool и semaphore (см. таблицу ниже).

### `NewLimiter`: rate и burst — разные вещи

```go
limiter := rate.NewLimiter(rate.Every(500*time.Millisecond), 2)
//                              ↑ скорость пополнения          ↑ ёмкость ведра
```

| Параметр | Значение | Смысл |
| -------- | -------- | ----- |
| `rate.Every(500ms)` | 1 токен каждые 500 ms | ~**2 операции в секунду** (не «2 токена каждые 500 ms») |
| `burst` | `2` | **Максимум** токенов в ведре; лишние не копятся выше burst |

При старте ведро **полное** (до burst) → первые `burst` вызовов могут пройти почти сразу, дальше — ~по rate.

### Типичный цикл жизни

1. Создать **один** `*rate.Limiter` на dependency (HTTP-клиент, shard БД).
2. Перед каждым вызовом: `err := limiter.Wait(ctx)`.
3. Если `err != nil` — context отменён **во время ожидания** → выйти, запрос не делать.
4. Иначе — выполнить операцию (I/O, лог, …).
5. В демо с N goroutine — `WaitGroup`: `Done` внутри goroutine, `Wait()` в main; на операцию — **тот же** `ctx`, что у caller.

```text
simulateRequest:
  Wait(ctx) ──err──► return
       │
      ok
       ▼
  реальный вызов
```

### `Wait` vs `Allow`

| | `Wait(ctx)` | `Allow()` |
| --- | --- | --- |
| Блокируется | да, ждёт токен | нет |
| Context | **обязателен** — прервать долгое ожидание | не нужен |
| Политика | «в очередь, дождись слота» | «слота нет — сразу отказ» |
| Когда | фоновые job, клиенты к API | HTTP 429, drop, skip без очереди |

`Wait` без context в API **нет** — только `Wait(ctx)`.

### Rate limit vs соседи

| | Rate limit | Worker pool / `SetLimit` | Semaphore |
| --- | --- | --- | --- |
| Ограничивает | **Как часто** (req/s) | **Сколько одновременно** | **Сколько одновременно** |
| Вопрос | «не чаще 10/s» | «не больше 5 параллельно» | «не больше N слотов» |
| 3 долгих запроса по 30 с | не про rate | 3 слота заняты | 3 слота заняты |

Часто **вместе**: pool ограничивает параллелизм, limiter — частоту к одному API.

Ticker «раз в секунду» — для **одного** цикла; для **многих** goroutine с общим лимитом — `rate.Limiter`, не ticker в каждой goroutine.

### Context и «не успели за deadline»

`Wait(ctx)` может стоять в очереди секундами. Если сработал `WithTimeout` / cancel — `Wait` возвращает `ctx.Err()`, goroutine **выходит**, не висит вечно. Запросов больше, чем успеет rate за время жизни ctx, — часть **не выполнится** (без Println / без I/O), но `WaitGroup` всё равно дождётся всех `Done()`.

### Типичные ошибки

- **Limiter на каждую goroutine** — каждая со своим «N/s», общего лимита нет.
- Путать **rate** и **burst** («каждые 500 ms добавляется 2» — неверно; добавляется **1**, burst — **потолок**).
- Ждать, что ведро **растёт бесконечно** при простое — нет, только до `burst`.
- `limiter.Wait(context.Background())` при отменяемом запросе — очередь не прервётся.
- **`Allow` vs pool**: pool не заменяет limit к API с quota по частоте.
- Limiter на goroutine + `time.After` в цикле вместо одного shared limiter.

Код: `patterns/rateLimiting.go`.

## Or-Channel

Идея: **несколько сигнальных каналов → один**. Выход «срабатывает», когда **готов любой** вход (первый побеждает). Это не поток данных — только «пора выходить / продолжать».

```text
after(2s) ──► a ──┐
after(5s) ──► b ──┼──► or(a, b, c) ──► merged ──► main: <-merged
after(8s) ──► c ──┘         │
                        close(merged) при первом сигнале
```

Сигнал обычно через **закрытие** `<-chan struct{}` или receive из done-канала. `ctx.Done()` — тот же тип: `<-chan struct{}`.

### Зачем

Когда источников «стоп» несколько — timeout, ручной cancel, heartbeat, sibling error — плоский `select` на 5–10 каналов не масштабируется. `or(a, b, c…)` **компонует** сигналы в один канал для одного `<-` или одного `select`.

На собесе: «как дождаться **любого** из N событий»; отличие от Or-Done и fan-in (см. ниже).

### Почему `chan struct{}`, а не `bool`

| | `chan struct{}` | shared `bool` |
| --- | --- | --- |
| `select` | да, нативно | нет |
| «Кто первый» | `select` выбирает готовую ветку | нужен mutex / polling |
| Broadcast | `close(ch)` будит всех ждущих | одна переменная — гонки |
| Payload | **0 байт** — только факт события | true/false — лишняя семантика |

Done-каналы и `context.Done()` в Go — идиома `struct{}`: **сигнал без данных**.

### `after` — источник сигнала

Вспомогательная функция «через `d` просигналить»:

```text
after(d):
  out := make(chan struct{})
  go func() { <-time.After(d); close(out) }()
  return out                    ← caller сразу получает канал
```

`after` **не блокируется** на `d` — ждёт goroutine в фоне. Иначе нельзя передать канал в `or` до истечения таймера.

### Типичный цикл жизни (`or`)

1. `switch len(channels)`: `0` → `nil`; `1` → вернуть канал as-is (без лишней goroutine).
2. `len >= 2`: `out := make(chan struct{})`, goroutine с **`select`**:
   - `case <-channels[0]:`
   - `case <-or(channels[1:]...):` — рекурсия на хвост.
3. После срабатывания любой ветки — **`close(out)`** (в goroutine, не `defer` при return из `or`).
4. Сразу `return out` — consumer делает `<-merged`.

```text
or(a, b, c)
    └── goroutine: select { <-a | <-or(b,c) } → close(out)
                              └── or(b,c): select { <-b | <-c }
```

**Не `for range` по слайсу каналов** — range идёт по элементам **по очереди**, а не «кто первый готов». Для этого только `select`.

### Or-Channel vs Or-Done vs fan-in

| | **Or-Channel** | **Or-Done** | **Fan-In** |
| --- | --- | --- | --- |
| Вход | N **сигналов** | данные + **один** `ctx` | N **потоков данных** |
| Выход | один **сигнал** | поток **тех же** данных | один поток **всех** значений |
| Вопрос | «кто **первый** из N?» | «пересылать, пока не **cancel**?» | «**собрать** результаты воркеров» |
| Данные | нет (только «пора») | `int`, `T`, … | `int`, `T`, … |

```text
OR-CHANNEL                    OR-DONE

  a ──┐                         in: 0,1,2,3...
  b ──┼──► ONE signal           ctx ──► out: 0,1,2... (копия до cancel)
  c ──┘    «первый wins»
```

Or-Done — стадия **pipeline** (read → forward + cancel). Or-Channel — **merge done-источников**, не пересылка бизнес-данных.

### Or-Channel vs один большой `select`

| | `or(a, b, c, …)` | `select { case <-a: case <-b: … }` |
| --- | --- | --- |
| Масштаб | рекурсия / композиция | раздувается при N |
| Переиспользование | функция | копипаста |
| Смысл | паттерн с именем | то же, но локально |

### Типичные ошибки

- **`defer close(out)` в начале `or`** — канал закрывается при return, consumer получает уже закрытый канал.
- **`after` без goroutine** или `<-time.After(d)` в теле `after` до `return` — caller не получает канал сразу; `or(after(2s), …)` блокируется последовательно.
- **`after(2)` без `time.Second`** — 2 **наносекунды**, не секунды.
- **Печатать канал, не `<-or(...)`** — паттерн не демонстрируется, main не ждёт.
- **`for range channels`** вместо `select` — не «первый готовый».
- Путать с **fan-in** — or для **сигналов**, fan-in для **данных**.
- **`or()` без аргументов** → `nil`; `<-nil` блокирует навечно.

### Утечки goroutine (демо vs прод)

После срабатывания `or` goroutine внутри `after` для «проигравших» таймеров ещё живут до своего `d` — для учебного дemo норм. В проде источники тоже должны уважать общий cancel.

Код: `patterns/orChanel.go`.

## Bridge

Идея: **развернуть канал каналов** `<-chan <-chan T` в **один плоский** `<-chan T`. Inner-каналы **приходят динамически** по wire; consumer читает один поток через `for range`.

```text
producer ──► chanStream (<-chan <-chan int)
                    │
                    ├── inner1: 1, 2
                    ├── inner2: 10, 20   ← по одному, со временем
                    └── inner3: 100
                    │
               bridge(ctx, chanStream)
                    │
                    ▼
                 out ──► consumer: for v := range out
```

Bridge — **не fan-out** (тот раздаёт один вход многим). Bridge — **сбор в один**, как fan-in, но источники **не известны заранее**.

### Зачем

Fan-in требует **фиксированный** набор: `fanIn(ch1, ch2, ch3)`. Bridge — когда каналы **появляются по ходу**: воркер закончил → прислал `<-chan Result` в общий `chanStream`; подписки подключаются runtime. Consumer не меняется — один `for range out`.

На собесе реже fan-in, но полезно: «чем `<-chan <-chan T` отличается от слайса каналов».

### Роли: producer, bridge, consumer

| Роль | Функция | Что делает |
| ---- | ------- | ---------- |
| **Producer** | `chanProducer` | создаёт inner, шлёт в `chanStream`, **`defer close(chanStream)`** |
| **Bridge** | `bridge` | `for { inner := <-chanStream; range inner → out }` |
| **Consumer** | `MainBridge` | `for v := range bridge(...)` — читает плоский поток |

Producer и bridge **сразу return** свой `out`; работа — в goroutine (как generator).

### Типичный цикл жизни (`chanProducer`)

1. `out := make(chan (<-chan int))`, `go func() { defer close(out); … }()`, `return out`.
2. Для каждой «партии»: пауза / `select` с `ctx`; создать **буферизованный** inner; fill + `close(inner)`; `out <- inner` (с `select` + `ctx`).
3. После всех партий goroutine выходит → **`close(chanStream)`** через defer.

Inner заполняют **до** `out <- inner` — иначе deadlock на небуферизованном send без reader.

### Типичный цикл жизни (`bridge`)

1. `out := make(chan int)`, goroutine, `defer close(out)`.
2. **`for { select { … } }`** — не один `select` на весь паттерн.
3. `inner, ok := <-chanStream`: **`!ok`** → producer закрыл stream → `return` (bridge закроет `out`).
4. `for el := range inner` — все значения inner в `out`.
5. Send с отменой: `select { case out <- el: case <-ctx.Done(): return }`.
6. Внешний `case <-ctx.Done()` — выход по cancel.

```text
for {
  select {
  case inner, ok := <-chanStream:
    if !ok { return }
    for el := range inner { out <- el (с ctx) }
  case <-ctx.Done():
    return
  }
}
```

### Как bridge узнаёт, что producer закончил

Закрытие `chanStream` — сигнал «inner больше не будет». Чтение **`inner, ok := <-chanStream`**: при закрытом пустом канале **`ok == false`**. Отдельный done-канал не нужен. Без `close(chanStream)` bridge **висит** на receive.

### Bridge vs fan-in vs fan-out

| | **Fan-Out** | **Fan-In** | **Bridge** |
| --- | --- | --- | --- |
| Направление | 1 → N | N → 1 | N → 1 (динамически) |
| Вход | один канал | `fanIn(a, b, c)` | `<-chan <-chan T` |
| Когда знаешь N | — | при старте | **по ходу** |
| Вопрос | распараллелить стадию | слить известные источники | развернуть **поток** каналов |

```text
FAN-OUT:   in ──► W1, W2, W3

FAN-IN:    ch1 ──┐
           ch2 ──┼──► out
           ch3 ──┘

BRIDGE:    chanStream ──► bridge ──► out
              (каналы «приезжают»)
```

Or-Done / Or-Channel сюда **не подменяют** bridge: они про cancel/сигналы, не про merge динамических **data**-каналов.

### Типичные ошибки

- **`case <-chanStream:` перед `for range`** — первый inner **выбрасывается**.
- **Один `select` без внешнего `for`** — обработан только **первый** inner, остальные lost.
- **`inner <- v` на небуферизованном** inner без reader — deadlock до `out <- inner`.
- **`chanStream` не закрыт** — bridge и consumer не завершаются.
- **`defer close(out)` bridge при return** до goroutine — consumer получает мёртвый канал.
- **`out <- el` без `ctx`** — зависание на send при cancel.
- Путать с **fan-in** — слайс каналов ≠ `<-chan <-chan T`.
- Путать с **fan-out** — bridge **собирает**, не раздаёт.

Код: `patterns/bridge.go`.

## Как паттерны склеиваются

В сервисе редко один паттерн — обычно **стек**:

```text
Generator
    ↓
Pipeline (parse → transform)
    ↓
Fan-Out (N воркеров)  +  Rate Limit на HTTP-клиент
    ↓
Fan-In или Bridge (собрать результаты)
    ↓
Or-Done / ctx (consumer ушёл — стадии не висят)
    ↓
errgroup (batch из нескольких независимых операций на запрос)
```

**Отмена** проходит сверху вниз: `context` из HTTP-handler → каждая стадия слушает `ctx.Done()` или обёрнута в `orDone`. **Or-Channel** — когда несколько источников «стоп» нужно слить в один `select`.

**Лимиты** — разные оси: worker pool / semaphore — **сколько параллельно**; rate limit — **как часто**; timeout — **сколько ждать одну операцию**.

## Шпаргалка: какой паттерн когда

| Задача | Паттерн |
| ------ | ------- |
| Лениво производить поток | Generator |
| Обработка цепочкой стадий | Pipeline |
| Ускорить одну стадию | Fan-Out |
| Собрать N известных каналов | Fan-In |
| Каналы приходят по ходу | Bridge |
| Много однотипных задач, лимит N | Worker Pool |
| Не ждать I/O вечно | Timeout / `context` |
| Стадия pipeline + cancel | Or-Done |
| N goroutine, одна ошибка отменяет остальных | errgroup |
| Не долбить API по RPS | Rate Limiting |
| Любой из N таймеров/done → выход | Or-Channel |

Если два паттерна «похожи» — задай вопрос **про данные или про сигнал**, **статично или динамично**, **частота или параллелизм**.

## Общий чеклист (перед «готово»)

Пробегись по любой новой concurrent-фиче:

1. **Context** — долгие операции и ожидания (`Wait`, sleep, I/O) слушают `ctx`; `defer cancel()` там, где создаёшь timeout.
2. **Закрытие** — канал закрывает **writer**; `for range` завершится; bridge/fan-in закрывают `out` только после всех writers.
3. **WaitGroup** — только `*sync.WaitGroup`; `Add` до `go`, `Done` внутри goroutine, `Wait` в caller.
4. **Send + cancel** — в pipeline вложенный `select` на `out <- v` и `<-ctx.Done()`, иначе goroutine зависнет.
5. **Нет утечек** — каждая goroutine имеет путь выхода: closed chan, `ctx`, или явный shutdown.
6. **Лимиты** — pool/semaphore на параллелизм; `rate.Limiter` **один** на dependency; не «горутина на каждый запрос без потолка».
7. **Проверка** — компилируется; поведение совпадает с заданием; под нагрузкой/cancel нет deadlock (смотри типичные ошибки в секциях выше).

## Типовые путаницы (сводка)

| Путают | На самом деле |
| ------ | ------------- |
| Fan-Out и Fan-In / Bridge | out: 1→N; in: N→1 (bridge — динамический N) |
| Rate limit и Worker Pool | частота vs параллелизм |
| Or-Done и Or-Channel | данные+cancel vs merge **сигналов** |
| Or-Channel и Fan-In | сигнал «первый wins» vs поток **значений** |
| Bridge и Fan-In | `<-chan <-chan T` vs слайс каналов при старте |
| `time.After` в case и «функция ждёт» | блокирует **select/receive**, не «останавливает» caller без `<-` |
| Закрытие chan consumer'ом | закрывает только **producer** |
