# Clean Architecture

Clean Architecture — подход к организации кода, при котором **бизнес-логика не зависит от базы данных, HTTP-фреймворка и других внешних деталей**. Благодаря этому правила приложения проще тестировать и менять независимо от инфраструктуры.

Главное правило:

> Зависимости направлены от внешних слоёв к внутренним.

```text
HTTP / CLI / gRPC
        ↓
   Use Cases
        ↓
    Entities

Database и внешние API подключаются через интерфейсы.
```

## Основные слои

### Entities — сущности

Содержат главные бизнес-объекты и правила предметной области. Они не должны знать, откуда пришёл запрос и где хранятся данные.

```go
type Order struct {
	ID     int64
	Status string
}
```

### Use Cases — сценарии приложения

Описывают действия системы: создать заказ, получить пользователя, провести оплату. Use case управляет сущностями и обращается к внешним зависимостям через интерфейсы.

```go
type OrderRepository interface {
	Save(ctx context.Context, order Order) error
}

type CreateOrder struct {
	repository OrderRepository
}
```

Интерфейс обычно объявляет слой, который его **использует**, а не пакет с конкретной реализацией.

### Interface Adapters — адаптеры

Преобразуют данные между бизнес-логикой и внешним миром:

- HTTP- и gRPC-хендлеры;
- реализации репозиториев;
- presenters и преобразователи DTO;
- клиенты внешних сервисов.

Хендлер превращает HTTP-запрос во входные данные use case. Репозиторий превращает вызов бизнес-слоя в SQL-запрос.

### Frameworks and Drivers — внешние детали

Самый внешний слой:

- база данных и драйвер;
- HTTP-фреймворк;
- брокер сообщений;
- файловая система;
- сторонние API.

Это заменяемые детали. Например, переход с PostgreSQL на другое хранилище не должен менять бизнес-правила.

## Инверсия зависимостей

Без инверсии бизнес-логика зависит от конкретной базы:

```text
service → postgres.Repository
```

В Clean Architecture внутренний слой определяет необходимый контракт, а внешний его реализует:

```text
service → Repository interface ← postgres.Repository
```

В Go реализация удовлетворяет контракту неявно: для этого импортировать пакет с интерфейсом не обязательно. Важнее, что service не импортирует конкретный postgres-адаптер. Реализацию передают при сборке приложения — в `main` или `internal/app`.

## Возможная структура Go-проекта

```text
cmd/api/main.go

internal/
├── order/
│   ├── entity.go
│   ├── service.go
│   └── repository.go       # интерфейс
├── repository/postgres/
│   └── order.go            # реализация интерфейса
├── transport/http/
│   └── order.go            # хендлер
└── app/
    └── app.go              # сборка зависимостей
```

Названия каталогов могут отличаться. Важнее направление зависимостей, чем буквальное копирование структуры.

## Пример прохождения запроса

```text
POST /orders
    ↓
HTTP handler разбирает запрос
    ↓
CreateOrder выполняет бизнес-сценарий
    ↓
OrderRepository сохраняет сущность
    ↓
PostgreSQL-адаптер выполняет SQL
```

Ответ проходит в обратную сторону. При этом use case ничего не знает об HTTP и PostgreSQL.

## Плюсы и минусы

Плюсы:

- бизнес-логику легко тестировать без базы и сервера;
- инфраструктуру можно заменять с меньшим количеством изменений;
- обязанности пакетов и направление зависимостей становятся понятнее;
- проект проще развивать при росте числа сценариев.

Минусы:

- появляется больше интерфейсов, типов и преобразований;
- для маленького приложения архитектура может быть избыточной;
- формальное разделение по папкам не помогает, если границы слоёв фактически нарушены.

## Что важно запомнить

Clean Architecture — не фиксированное дерево каталогов. Её основа — независимая бизнес-логика и зависимости, направленные внутрь. В Go стоит начинать с простой структуры и выделять слои тогда, когда они действительно помогают разделить ответственность.

На собеседовании объясни отличие направления вызова от зависимости пакетов, пользу небольших интерфейсов и цену абстракций. Смена БД не становится бесплатной: различия транзакций, модели данных и запросов всё равно нужно учитывать. Граница транзакции определяется бизнес-сценарием; все участвующие операции должны использовать одну транзакцию.
