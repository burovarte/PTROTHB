# Dependency Injection

Dependency Injection (DI, внедрение зависимостей) — способ передавать объекту его зависимости **снаружи**, а не создавать их внутри объекта.

Зависимостью может быть репозиторий, HTTP-клиент, логгер, конфигурация или другой сервис.

## Без Dependency Injection

```go
type OrderService struct {
	repository *PostgresOrderRepository
}

func NewOrderService() *OrderService {
	return &OrderService{
		repository: NewPostgresOrderRepository(),
	}
}
```

`OrderService` сам создаёт конкретный PostgreSQL-репозиторий. Из-за этого он:

- жёстко связан с PostgreSQL;
- сложнее тестируется;
- управляет не только бизнес-логикой, но и созданием инфраструктуры;
- требует изменения при замене реализации репозитория.

## С Dependency Injection

Сервис получает готовую зависимость через конструктор:

```go
type OrderRepository interface {
	Save(ctx context.Context, order Order) error
}

type OrderService struct {
	repository OrderRepository
}

func NewOrderService(repository OrderRepository) *OrderService {
	return &OrderService{repository: repository}
}
```

Теперь сервис знает только необходимый ему контракт. Конкретную реализацию выбирает код, который собирает приложение.

```go
repository := NewPostgresOrderRepository(db)
service := NewOrderService(repository)
handler := NewOrderHandler(service)
```

Такое место называют **composition root** — точкой сборки зависимостей. В Go ей обычно служит `main` или пакет `internal/app`.

## Основные способы внедрения

### Через конструктор

Основной и предпочтительный вариант:

```go
func NewService(repository Repository, logger Logger) *Service {
	return &Service{
		repository: repository,
		logger:     logger,
	}
}
```

Плюсы:

- обязательные зависимости видны в сигнатуре;
- нельзя получить объект без необходимых компонентов;
- объект удобно тестировать;
- поля можно оставить неэкспортируемыми.

### Через метод или поле

```go
service.SetLogger(logger)
```

Такой способ подходит для необязательной или изменяемой зависимости, но обязательную зависимость легко забыть установить. Публичные поля ещё и позволяют привести объект в некорректное состояние.

### Через параметры функции

Если зависимость нужна только одной операции, её можно передать прямо в функцию:

```go
func ProcessOrder(ctx context.Context, repository Repository, id int64) error
```

Для небольшого кода это проще, чем создавать отдельную структуру.

## DI и интерфейсы

DI не требует интерфейса для каждой зависимости. Конкретный тип можно внедрять напрямую:

```go
func NewHandler(logger *slog.Logger) *Handler
```

Интерфейс полезен, когда вызывающему коду действительно нужны разные реализации или тестовая подмена. В Go интерфейс обычно объявляют рядом с кодом, который его использует, и делают минимальным:

```go
type OrderFinder interface {
	FindByID(ctx context.Context, id int64) (Order, error)
}
```

Не стоит создавать большой интерфейс на все методы репозитория, если сервису нужен только один.

## Тестирование

Благодаря DI в тест можно передать простую подмену без настоящей базы данных:

```go
type repositoryStub struct {
	order Order
}

func (r repositoryStub) FindByID(context.Context, int64) (Order, error) {
	return r.order, nil
}

service := NewOrderService(repositoryStub{
	order: Order{ID: 1},
})
```

Тест проверяет бизнес-логику отдельно от сети и хранилища.

## Ручной DI и контейнеры

В Go зависимости часто собирают вручную: вызовы конструкторов просты, явно видны и проверяются компилятором.

В больших приложениях для генерации кода может использоваться Wire. Runtime-контейнеры также существуют, но добавляют неявность и обычно нужны реже. Начинать лучше с ручной сборки.

## Связь с Clean Architecture

Dependency Injection помогает соблюдать направление зависимостей:

```text
handler → service → repository interface
                         ↑
                postgres repository
```

Внутренний слой определяет нужный контракт, внешний слой реализует его, а composition root соединяет реализации. Это практическое применение принципа инверсии зависимостей.

## Типичные ошибки

- создание базы данных или клиента прямо внутри бизнес-сервиса;
- глобальные зависимости и singleton-переменные;
- интерфейс для каждого типа без практической необходимости;
- огромные интерфейсы вместо маленьких контрактов потребителя;
- конструктор с десятками аргументов — часто признак слишком большой ответственности объекта;
- DI-контейнер, скрывающий создание зависимостей и ошибки до момента запуска;
- передача зависимостей через `context.Context` — context предназначен для отмены, deadline и метаданных запроса, а не для DI.

## Что важно запомнить

DI означает: **объект получает зависимости извне**. В Go основной способ — явные конструкторы и ручная сборка в `main` или `internal/app`. Интерфейсы добавляют со стороны потребителя и только там, где нужна абстракция или подмена реализации.
