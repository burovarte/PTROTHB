# MongoDB

**MongoDB** — документная база данных. Вместо строк с фиксированными колонками она хранит документы BSON: объекты с полями, вложенными объектами и массивами. **Коллекция** объединяет документы, например `playlists`.

Для Go backend достаточно понимать модель данных, индексы, атомарность и выбор между MongoDB и PostgreSQL. Администрирование большого кластера — отдельная тема.

## Как выглядят данные

```json
{
  "_id": "playlist-42",
  "owner_id": "user-7",
  "title": "Для работы",
  "tracks": [{"track_id": "track-1", "position": 1}],
  "version": 3
}
```

`_id` — уникальный идентификатор документа; обычно драйвер генерирует `ObjectId`, но возможны другие типы. JSON выше иллюстрирует структуру, а не все типы BSON.

**Гибкая схема не означает отсутствие схемы.** Приложение всё равно ожидает определённые поля и типы; MongoDB также поддерживает серверную валидацию документов.

## Вложить данные или хранить ссылку

| Подход | Когда подходит | Цена |
|---|---|---|
| Вложенные документы | Данные читают и изменяют вместе, размер ограничен | Дублирование и рост документа |
| Ссылка по ID | Общие сущности, независимые обновления, большие связи | Дополнительные запросы или `$lookup` |

В плейлисте можно хранить позиции и ID треков, а общую информацию о треке — отдельно. Не стоит вкладывать бесконечную историю прослушиваний в документ пользователя: размер документа ограничен 16 MiB.

Модель выбирают **под запросы и границы атомарного изменения**, а не просто переводят каждую SQL-таблицу в коллекцию.

## Запросы и индексы

Пример для `mongosh`:

```javascript
db.playlists.createIndex({owner_id: 1, updated_at: -1})
db.playlists.find({owner_id: "user-7"}).sort({updated_at: -1}).limit(20)
```

Составной индекс помогает фильтровать плейлисты владельца и возвращать их по времени. Без подходящего индекса сервер может просматривать всю коллекцию. Индексы занимают место и замедляют запись; создавать индекс на каждое поле не нужно.

`explain("executionStats")` показывает план и фактическую работу запроса. Сравнивают количество просмотренных документов и ключей с количеством возвращённых документов. `COLLSCAN` — сканирование коллекции, `IXSCAN` — использование индекса.

**Aggregation pipeline** — последовательность этапов обработки, например `$match` → `$group` → `$sort`. `$lookup` позволяет соединять коллекции: утверждение «в MongoDB нет join» неверно.

## Атомарность и конкурентные изменения

Изменение **одного документа атомарно**, даже если меняет несколько его полей. Но последовательность «прочитать → вычислить → записать» сама по себе не защищена от конкуренции.

```javascript
db.playlists.updateOne(
  {_id: "playlist-42", version: 3},
  {$set: {title: "Фокус"}, $inc: {version: 1}}
)
```

Это **оптимистическая блокировка**: обновляем только ожидаемую версию. Если `matchedCount` равен нулю, документ удалён или кто-то изменил его раньше; нельзя сообщать об успешном обновлении.

Для согласованных изменений нескольких документов существуют транзакции. Они требуют подходящего развёртывания — replica set или sharded cluster — и не заменяют продуманную модель данных.

## Репликация и шардирование

- **Репликация** — копии данных на нескольких узлах. В replica set запись принимает primary, secondary воспроизводят изменения; при отказе возможен выбор нового primary.
- **Шардирование** — распределение разных частей данных между узлами по shard key. Оно решает задачу масштаба, а не является синонимом резервной копии.
- **Write concern** определяет, каких подтверждений ждать при записи. **Read concern** — какие гарантии видимости требовать при чтении. Чтение с secondary может отставать.

## Практика в Go

Обычно создают один переиспользуемый `mongo.Client`: драйвер управляет пулами соединений к серверам. На операции передают `context` с дедлайном, проверяют ошибки, закрывают курсоры и освобождают клиент при завершении приложения.

Структуры размечают `bson`-тегами. Для фильтров и обновлений используют типы драйвера, а не собирают выражения из непроверенного пользовательского ввода. При чтении примеров проверяют major-версию драйвера: API разных версий может отличаться.

## Что важно на собеседовании

1. **Почему не PostgreSQL?** MongoDB удобна для документной модели с ограниченными вложенными данными. Для большого числа связей, ограничений и привычных SQL-транзакций PostgreSQL часто проще. «NoSQL быстрее SQL» без нагрузки и запроса ничего не означает.
2. **Есть ли транзакции?** Да; атомарность одного документа доступна без многодокументной транзакции.
3. **Чем репликация отличается от шардирования?** Копии одних данных против распределения разных данных.
4. **Почему запрос медленный?** Проверить фильтр, сортировку, индекс, план, объём результата и количество обращений к БД.

**Запомнить:** документная модель → запросы → индексы → границы атомарности. MongoDB не отменяет проектирование схемы и обработку конфликтов.
