# Тестирование Go-сервисов

**Тест** автоматически проверяет наблюдаемое поведение программы. Важно проверять не только успешный ответ, но и ошибки, границы входных данных, отмену и повторное выполнение.

Профилирование и поиск гонок разобраны отдельно: [pprof и race detector](<22. Тестирование: pprof и race detector.md>).

## Какие бывают тесты

| Вид | Что проверяет | Пример |
|---|---|---|
| Unit | Небольшую логику изолированно | Нельзя добавить трек в чужой плейлист |
| Integration | Взаимодействие компонентов | Репозиторий и настоящий PostgreSQL |
| End-to-end | Пользовательский сценарий целиком | HTTP → сервис → БД → ответ |

Много быстрых unit-тестов и меньше дорогих сквозных проверок — полезный ориентир, не обязательное численное соотношение. Одни mocks не проверяют SQL и конфигурацию, одни end-to-end тесты дают медленную и неудобную диагностику.

## Table-driven tests

Тесты находятся в `*_test.go`, функции имеют вид `TestXxx(t *testing.T)`. **Табличный тест** описывает несколько случаев данными, а не копирует одинаковые проверки.

Самодостаточный учебный пример для файла `limit_test.go`:

```go
package playlist

import "testing"

func normalizeLimit(n int) int {
    if n <= 0 { return 20 }
    if n > 100 { return 100 }
    return n
}

func TestNormalizeLimit(t *testing.T) {
    cases := []struct {
        name string
        input, want int
    }{
        {"negative", -1, 20},
        {"default", 0, 20},
        {"minimum", 1, 1},
        {"maximum", 100, 100},
        {"too large", 101, 100},
    }
    for _, tc := range cases {
        t.Run(tc.name, func(t *testing.T) {
            if got := normalizeLimit(tc.input); got != tc.want {
                t.Errorf("got %d, want %d", got, tc.want)
            }
        })
    }
}
```

В реальном проекте проверяемая функция находится в обычном `.go`-файле. Структура проверки: подготовить данные → выполнить действие → сравнить результат. `t.Error` помечает неуспех и продолжает, `t.Fatal` прекращает текущий тест; `Fatal` нельзя вызывать из рабочей дочерней горутины вместо передачи ошибки тесту.

## Stub, fake, mock

- **Stub** возвращает заранее заданный ответ, например ошибку БД.
- **Fake** — простая рабочая замена, например репозиторий в памяти.
- **Mock** проверяет ожидаемое взаимодействие, например вызов `Save` с нужным заказом.

Подмена внедряется через небольшой интерфейс, принадлежащий потребителю. Не нужно мокать каждую внутреннюю функцию: такой тест ломается при рефакторинге, хотя поведение не меняется. Проверка результата важнее точной последовательности несущественных вызовов.

## HTTP и БД

`httptest.NewRecorder` вместе с `httptest.NewRequest` позволяет вызвать handler без открытия порта. `httptest.NewServer` запускает локальный тестовый HTTP-сервер — удобно проверять собственного клиента.

Проверять нужно status, заголовки, тело и отсутствие нежелательных изменений, например записи при `403`. Для клиента — также timeout, некорректный JSON и ответ `500`.

SQL-репозиторий проверяют на PostgreSQL с применёнными миграциями, например в отдельном тестовом контейнере. SQLite не воспроизводит полностью синтаксис, блокировки и изоляцию PostgreSQL. Данные изолируют отдельной схемой/БД либо rollback тестовой транзакции, если все операции действительно используют её.

## Детерминированность

- `t.Cleanup` закрывает ресурсы; `t.TempDir` создаёт изолированные временные файлы.
- `t.Parallel` подходит только независимым тестам. Общие map, глобальная конфигурация и одни строки БД могут создавать гонки между тестами.
- Не ждать готовности произвольным `time.Sleep`: использовать сигнал, канал или проверку условия с ограниченным временем.
- Время и генерацию ID при необходимости передавать как зависимости. Для подходящих concurrent-тестов есть `testing/synctest` в современных версиях Go; изучать после обычной синхронизации тестов.

## Coverage, fuzzing и benchmark

**Coverage** показывает, какие участки кода выполнялись тестами, но не качество проверок. 100% покрытия не доказывает корректность и не охватывает все возможные комбинации входных данных.

**Fuzzing** генерирует множество входов для проверки свойства: например декодер не паникует на произвольных байтах, а кодирование/декодирование сохраняет допустимое значение. Начальные примеры добавляют через `f.Add`, проверку — через `f.Fuzz`.

**Benchmark** измеряет стоимость операции: время и аллокации. Подготовку отделяют от измеряемой работы; в Go 1.24+ можно использовать `b.Loop()`. Сравнивают несколько прогонов в похожих условиях, а не один случайный результат.

```bash
go test ./...
go test -race ./...
go test -coverprofile=coverage.out ./...
go tool cover -func=coverage.out
go test -run '^TestNormalizeLimit$' -count=1 ./...
go test -run '^$' -bench . -benchmem ./...
# В пакете, где определён FuzzDecode:
go test -fuzz '^FuzzDecode$' -fuzztime=10s .
```

## Что важно на собеседовании

1. **Mock БД или настоящая БД?** Для бизнес-логики — подмена, для SQL и транзакций — integration с настоящей СУБД.
2. **Что проверить кроме happy path?** Пустой/невалидный ввод, not found, отсутствие прав, конфликт, timeout, повторы и конкурентное изменение.
3. **Почему тест иногда падает?** Проверить общее состояние, порядок выполнения, работу со временем и незавершённые горутины.
4. **Тесты зелёные — гонок нет?** Нет; `-race` видит только выполненные пути, а логическая гонка возможна и без data race.

**Запомнить:** тестировать контракт, изолировать окружение, проверять отказы. Тест должен помогать менять код, а не фиксировать каждую деталь реализации.
