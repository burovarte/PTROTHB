# Структуры и интерфейсы

В Go нет классов в стиле Java. Данные описывают через **struct**, поведение — через **методы** и **интерфейсы**. Вместе они дают композицию и полиморфизм без наследования.

## Struct

Структура — набор полей, способ сгруппировать связанные данные:

```go
type User struct {
    ID   int
    Name string
}

u := User{ID: 1, Name: "Ann"}
fmt.Println(u.Name)
```

Поля читают и пишут через точку. Можно взять указатель: `p := &u`, дальше `p.Name` — Go сам разыменует. Zero value у struct — структура, где каждое поле в своём zero value (`User{}` уже валиден).

Struct — **value type**: присваивание и передача в функцию копируют поля. Для мутации и больших объектов обычно передают `*User`. Нюанс: даже при копии struct поля-ссылки (slice, map, pointer) шарят underlying data.

Поля с заглавной буквы экспортируются из пакета, со строчной — нет. Теги (`json:"name"`) — метаданные для `encoding/json` и других библиотек через reflect.

Встраивание (embedding) даёт композицию и promotion полей/методов — это не наследование:

```go
type Logger struct{}

func (l *Logger) Log(msg string) { fmt.Println(msg) }

type Service struct {
    *Logger
}

s := Service{Logger: &Logger{}}
s.Log("hi") // поднятый метод
```

## Интерфейсы

Интерфейс — набор **сигнатур методов** (имя + аргументы + возвраты, без тела):

```go
type Stringer interface {
    String() string
}
```

Значение интерфейса может хранить любой тип, у которого есть эти методы. Реализация **неявная**: нет `implements`. Достаточно совпадения method set.

```go
type User struct{ Name string }

func (u User) String() string {
    return u.Name
}

var s fmt.Stringer = User{Name: "Ann"} // ок
```

Связь проверяется в момент использования (присваивание / передача в функцию), а не когда объявляешь struct. Определение интерфейса и реализация могут жить в разных пакетах без предварительной договорённости.

Идиомы Go:

- интерфейс объявляет **потребитель**, маленьким (1–3 метода);
- **принимай интерфейсы, возвращай конкретные типы**;
- не плоди интерфейсы «на будущее», если одна реализация и нет подмены.

## Method set: `T` vs `*T`

От method set зависит, реализует ли тип интерфейс.

| Тип  | Какие методы в наборе       |
| ---- | --------------------------- |
| `T`  | методы с receiver `(T)`     |
| `*T` | методы с `(T)` **и** `(*T)` |

Поэтому:

```go
type Counter struct{ n int }

func (c *Counter) Inc() { c.n++ }

type Incer interface{ Inc() }

var i Incer
i = &Counter{} // ок
// i = Counter{} // ошибка: у T нет Inc
```

При обычном вызове `c.Inc()` на переменной типа `Counter` компилятор часто сам сделает `(&c).Inc()`, если значение addressable. Но **интерфейс строже**: в него нельзя «доложить» pointer-метод через value.

## Что внутри интерфейса: `(type, value)`

Интерфейсное значение хранит пару **(конкретный тип, значение)**. Отсюда классическая ловушка:

```go
var p *User = nil
var i fmt.Stringer = p

fmt.Println(i == nil) // false: тип заполнен, значение nil
```

Интерфейс `nil`, только если и тип, и значение nil. Часто всплывает на примере `error`.

Пустой интерфейс — `any` / `interface{}`: методов нет, подходит любой тип. Дальше обычно нужны type assertion / type switch:

```go
s, ok := i.(string)

switch v := i.(type) {
case string:
    // ...
case int:
    // ...
}
```

## Struct + interface вместе

Типичный дизайн сервиса:

```go
type Mailer interface {
    Send(to, body string) error
}

type UserService struct {
    mail Mailer
}

func (s UserService) Register(email string) error {
    return s.mail.Send(email, "Добро пожаловать")
}
```

В проде кладут SMTP-реализацию, в тесте — фейк. `UserService` зависит от поведения, не от конкретной отправки.

Проверка на этапе компиляции:

```go
var _ Mailer = (*SMTPMailer)(nil)
```

`error` и `fmt.Stringer` / `io.Reader` — тоже интерфейсы из stdlib на той же идее.

## Фраза на собес

Struct хранит данные (value, копируется). Интерфейс описывает поведение через сигнатуры методов и реализуется неявно. Method set решает, подойдёт ли `T` или только `*T`. Внутри интерфейса пара `(type, value)` — отсюда nil-ловушка. Принимай маленькие интерфейсы у потребителя, возвращай concrete types.
