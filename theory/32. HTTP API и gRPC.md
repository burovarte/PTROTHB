# HTTP API и gRPC

**API** — контракт взаимодействия программ: допустимые запросы, ответы, ошибки и правила совместимости. В backend распространены HTTP API с JSON и gRPC с типизированными сообщениями.

Сетевой базис вынесен отдельно: [DNS, TCP, TLS и HTTP](<19. Компьютерные сети.md>).

## HTTP API и REST

**REST** — архитектурный стиль работы с ресурсами, а не название любой ручки с JSON. На практике от разработчика ждут понятных ресурсов, методов, статусов и согласованного контракта.

| Запрос | Смысл | Типичный успешный ответ |
|---|---|---|
| `GET /playlists/42` | Получить ресурс | `200` + JSON |
| `POST /playlists` | Создать ресурс | `201` + ID/Location |
| `PUT /playlists/42` | Заменить представление по контракту | `200` или `204` |
| `PATCH /playlists/42` | Частично изменить | `200` или `204` |
| `DELETE /playlists/42` | Удалить | `204` |

**Safe** означает, что метод не запрашивает изменение состояния: например GET. **Idempotent** — повтор не добавляет новый предполагаемый эффект: например PUT и DELETE. Это не требование одинаковых ответов: повтор DELETE может вернуть `404`. POST и PATCH не идемпотентны автоматически.

Ошибки: `400` — некорректный запрос, `401` — нет подходящей аутентификации, `403` — нет права, `404` — ресурс не найден, `409` — конфликт состояния, `429` — превышение лимита, `500` — внутренняя ошибка. Подробности SQL, stack trace и секреты клиенту не возвращают.

**Stateless** означает, что серверу не нужна скрытая история диалога с этим клиентом для понимания запроса. Это не запрет хранить бизнес-данные в БД. Формат JSON и ошибки удобно фиксировать в OpenAPI.

## Обработчик в Go

`http.Handler` имеет метод `ServeHTTP(http.ResponseWriter, *http.Request)`. **Middleware** оборачивает handler и добавляет общую логику: request ID, логирование, метрики, аутентификацию, ограничения и восстановление после panic.

Порядок обработки важен: ограничить размер тела → разобрать и проверить вход → проверить права на ресурс → вызвать бизнес-логику → преобразовать результат в HTTP-ответ.

- Контекст берут из `r.Context()` и передают вниз; не заменяют его на `Background`.
- Тело запроса ограничивают через `http.MaxBytesReader`; ошибки JSON проверяют. При строгом контракте запрещают неизвестные поля и дополнительные JSON-значения после первого.
- Заголовки/status записывают до тела. Первая запись тела без `WriteHeader` означает `200`; поздний `WriteHeader(500)` уже не исправит ответ.
- Handler вызывается конкурентно: общее состояние требует синхронизации. После возврата нельзя продолжать писать в `ResponseWriter` из фоновой горутины.
- Клиент и transport переиспользуют; проверяют HTTP status отдельно от ошибки транспорта и закрывают тело ответа.

## gRPC

**RPC (remote procedure call)** — вызов удалённой процедуры как метода клиента. В типичном gRPC контракт описан в Protocol Buffers, из `.proto` генерируются типы и код клиента/сервера; транспорт — HTTP/2.

```protobuf
syntax = "proto3";
package playlist.v1;

service PlaylistService {
  rpc GetPlaylist(GetPlaylistRequest) returns (Playlist);
}
message GetPlaylistRequest { int64 id = 1; }
message Playlist {
  int64 id = 1;
  string title = 2;
}
```

Это иллюстрация контракта: для генерации Go-кода нужны также `go_package`, генераторы и настройки проекта.

Есть четыре формы вызова: **unary** — один запрос/ответ, **server streaming**, **client streaming** и **bidirectional streaming**. Для общего кода используют **interceptors**, похожие по роли на HTTP middleware.

| | HTTP API + JSON | gRPC |
|---|---|---|
| Контракт | Обычно OpenAPI и договорённости | `.proto` и генерация кода |
| Отладка | Удобно читать JSON через curl | Нужны средства вроде grpcurl |
| Типичное применение | Публичные/браузерные API | Внутренние типизированные вызовы и streams |
| Ошибки | HTTP statuses + тело | gRPC status codes + details |

gRPC не всегда быстрее: результат зависит от размера сообщений, сети и работы сервиса. Браузер не вызывает обычный gRPC так же, как JSON API: обычно нужен gRPC-Web или gateway.

## Дедлайны и совместимость

У gRPC **нет дедлайна по умолчанию**. Go-клиент передаёт context с ограничением времени и переиспользует `ClientConn`. Сервер должен учитывать отмену в запущенной им работе. Для ошибок используют `codes.NotFound`, `InvalidArgument`, `DeadlineExceeded` и другие коды, а не сравнение текста.

В protobuf номер поля — часть wire-контракта: нельзя перенумеровывать или переиспользовать удалённые номера. Удалённые поля резервируют через `reserved`. Добавление поля часто совместимо на уровне wire-формата, но новую обязательность бизнес-правил надо согласовать со старыми клиентами.

Повторы после timeout могут дублировать эффект. Для записи нужны условия безопасного повтора: [идемпотентность и retry](<30. Паттерны микросервисов.md>).

## Минимум безопасности

- **Аутентификация:** кто обращается? **Авторизация:** разрешено ли ему действие? Валидный токен пользователя не разрешает читать чужой плейлист: проверяется владелец/право на конкретный объект.
- **JWT** — формат токена. Обычный подписанный JWT не зашифрован: payload можно прочитать. Проверяют подпись с разрешённым алгоритмом, `exp`, ожидаемые `iss`/`aud`; при необходимости также `nbf`. Сам формат не решает отзыв токенов.
- **OAuth 2.0** описывает делегирование доступа, **OpenID Connect** добавляет протокол идентификации. Это не синонимы JWT.
- TLS защищает передачу. SQL используют с параметрами; для загружаемых по пользовательскому URL ресурсов учитывают **SSRF** — попытку заставить сервер обращаться к внутренней сети.
- **CORS** — браузерное ограничение чтения ответов, не авторизация API. При cookie-аутентификации нужна защита от **CSRF** — выполнения действия чужим сайтом от имени пользователя.
- Пароли хранят как результат специализированного password hashing, например Argon2id, а не plaintext или обычный SHA-256. Ключи и токены не пишут в логи.

## Что важно на собеседовании

1. **Почему transport error и HTTP 500 не одно?** При 500 HTTP-обмен мог успешно завершиться; `Client.Do` не обязан вернуть `err`.
2. **PUT или PATCH?** Замена представления против частичного изменения; конкретную семантику фиксирует контракт.
3. **Почему JWT недостаточно для доступа?** После проверки личности нужно проверить права на действие и объект.
4. **Что сломает старого gRPC-клиента?** Несовместимые поля/номера и новые бизнес-требования, которым старый запрос не соответствует.

**Запомнить:** контракт → валидация → права → дедлайн → предсказуемая ошибка → совместимость. Выбор транспорта не решает эти задачи автоматически.
