# Docker и Docker Compose

**Docker** позволяет упаковать приложение вместе с его окружением в контейнер. Благодаря этому Go-сервис запускается одинаково на компьютере разработчика, в CI и на сервере.

## Основные понятия

| Термин | Смысл |
|---|---|
| **Image (образ)** | Неизменяемый шаблон: приложение, библиотеки и настройки для запуска |
| **Container (контейнер)** | Запущенный экземпляр образа |
| **Dockerfile** | Рецепт сборки образа |
| **Volume (том)** | Данные вне жизненного цикла контейнера |
| **Docker Compose** | Описание и запуск нескольких связанных контейнеров одним YAML-файлом |

Контейнер не является виртуальной машиной: он использует ядро хостовой ОС, но изолирует процессы, сеть и файловую систему приложения.

## Dockerfile для Go-сервиса

```dockerfile
# Сборка приложения
FROM golang:1.24 AS build
WORKDIR /app

COPY go.mod go.sum ./
RUN go mod download

COPY . .
RUN CGO_ENABLED=0 go build -o server ./cmd/api

# Финальный образ: только бинарный файл
FROM alpine:3.22
WORKDIR /app
COPY --from=build /app/server ./server

EXPOSE 8080
CMD ["./server"]
```

Это **multi-stage build**: на первом этапе есть компилятор Go, на втором — только готовый бинарник. Финальный образ получается меньше и содержит меньше ненужных инструментов.

Полезный `.dockerignore` не даёт отправлять в контекст сборки лишние файлы:

```text
.git
.env
tmp/
bin/
```

Собрать и запустить образ можно так:

```bash
docker build -t playlist-api .
docker run --rm -p 8080:8080 playlist-api
```

`-p 8080:8080` публикует порт контейнера наружу в формате `порт_хоста:порт_контейнера`.

## Docker Compose: Go-сервис и PostgreSQL

Когда для приложения нужны сервис и БД, вручную запускать контейнеры неудобно. Compose описывает их как один проект.

```yaml
services:
  api:
    build: .
    ports:
      - "8080:8080"
    environment:
      DATABASE_URL: postgres://app:app@postgres:5432/app?sslmode=disable
    depends_on:
      postgres:
        condition: service_healthy

  postgres:
    image: postgres:17
    environment:
      POSTGRES_DB: app
      POSTGRES_USER: app
      POSTGRES_PASSWORD: app
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d app"]
      interval: 5s
      timeout: 3s
      retries: 5

volumes:
  postgres_data:
```

```mermaid
flowchart LR
    C[Client] -->|localhost:8080| A[api container]
    A -->|postgres:5432| P[postgres container]
    P --> V[(postgres_data volume)]
```

Внутри сети Compose сервисы обращаются друг к другу по имени сервиса. Поэтому Go-приложение подключается к `postgres:5432`, а не к `localhost:5432`: `localhost` внутри контейнера означает сам контейнер `api`.

Команды:

```bash
docker compose up --build
docker compose up -d
docker compose logs -f api
docker compose down
```

`down` удалит контейнеры и сеть, но именованный том останется. Команда `docker compose down -v` удалит также тома — для данных PostgreSQL это разрушительное действие.

## Volumes, переменные и сеть

- Без тома данные внутри контейнера исчезнут после его удаления. PostgreSQL нужен именованный volume.
- Переменные окружения подходят для конфигурации. Пароли не стоит вшивать в образ или коммитить в Git; для локальной разработки используют неотслеживаемый `.env`, в production — менеджер секретов.
- Внешние порты публикуют только тем сервисам, к которым должен обращаться хост. PostgreSQL для локальной разработки можно не публиковать, если доступ к нему нужен лишь `api`.

## Типичные ошибки

- Считать, что `depends_on` без healthcheck означает готовность БД. Контейнер мог стартовать, но PostgreSQL ещё не принимать подключения.
- Использовать `latest`: лучше фиксировать версию образа, например `postgres:17`.
- Хранить данные БД только внутри контейнера.
- Копировать в образ `.env`, ключи или весь репозиторий без `.dockerignore`.
- Путать порт хоста с портом контейнера и использовать `localhost` для связи двух контейнеров.

## Что важно на собеседовании

1. Образ — шаблон, контейнер — его запущенный экземпляр.
2. Dockerfile собирает один образ; Docker Compose запускает несколько связанных сервисов.
3. Volume сохраняет данные после пересоздания контейнера.
4. Сервисы Compose общаются по DNS-имени сервиса во внутренней сети.
5. Multi-stage build уменьшает финальный образ и отделяет сборку от запуска.
