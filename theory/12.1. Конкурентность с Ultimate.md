## Конкурентность ≠ параллелизм

**Конкурентность** — про то, что инструкции могут выполняться **в неопределённом порядке** (out of order), а результат при этом остаётся корректным. Это способ *иметь дело* со многими задачами сразу.

**Параллелизм** — когда две и больше инструкций реально бегут **одновременно** (нужны ≥2 OS/hardware thread и ≥2 горутины на разных потоках).

Цитата Уильяма Кеннеди: параллелизм — физически делать несколько вещей в одно время; конкурентность — про неопределённый порядок выполнения.

Имеет смысл вводить конкурентность только если out-of-order даёт **достаточный выигрыш** за сложность. Не каждая задача «лучше с `go`».

---

## Горутины

Горутина — функция, которую **планировщик Go** создаёт и планирует независимо. Это не OS-поток один-в-один: runtime мультиплексирует много горутин на меньшее число потоков ОС.

Запуск:

```go
go doWork()
```

Аргументы вычисляются в текущей горутине; сама функция уже бежит отдельно.

Ключевые установки Ultimate Go:

- **Всегда знать**, сколько горутин запущено и **как они завершаются**.
- Приложение должно стартовать и гаснуть **с целостностью**: до возврата из `main` свои горутины лучше дождаться; уметь controlled shutdown под нагрузкой.
- По умолчанию горутина **не должна переживать** функцию, из которой её создали (Peter Bourgon): кто завёл — тот и отвечает за lifetime.

## Scheduler Semantics (из раздела Goroutines)

В [туре](https://tour.ardanlabs.com/tour/rus/goroutines/1) это отдельный блок: не синтаксис `go`, а **как понимать поведение** планировщика. У Кеннеди: *mechanics* — как устроено; *semantics* — какое поведение из этого следует для твоего кода.

### G / M / P

При старте runtime смотрит, сколько OS-потоков может реально бежать параллельно (по числу доступных ядер), и для каждого создаёт:

- **M** (*machine*) — OS-thread;
- **P** (*processor*) — логический процессор / execution context внутри программы;
- **G** (*goroutine*) — путь выполнения инструкций *на* M (как M исполняет инструкции на железе).

Появляется слой над OS-scheduler: контроль исполнения во многом на уровне приложения. Подробности — [Scheduling In Go I–III](https://www.ardanlabs.com/blog/2018/08/scheduling-in-go-part1.html).

`GOMAXPROCS` задаёт, сколько P (сколько потоков одновременно исполняют Go-код). `GOMAXPROCS(0)` возвращает текущее значение — в контейнере с CPU quota важно, чтобы оно совпадало с реальными потоками, иначе программа «дышит» хуже, чем могла бы.

### Словарь семантики

| Термин | Смысл |
|--------|--------|
| **Work** | набор инструкций приложения; выполняется потоками |
| **Thread** | путь исполнения, который планируют и гоняют на железе |
| **Running** | поток (с G на M) сейчас исполняет инструкции |
| **Runnable** | хочет CPU, сидит в run queue |
| **Waiting** | ждёт событие; планировщику «не интересен», пока не проснётся |
| **CPU-bound** | работа сама по себе почти не уходит в Waiting (например, fibonacci) |
| **I/O-bound** | естественно уходит в Waiting (сеть, диск, URL) |
| **Synchronization** | горутины делят память и должны ходить по очереди → mutex/atomic; иначе data race |
| **Orchestration** | горутины **сигналят** друг другу (с данными или без) → каналы, WaitGroup; иначе нет гарантий, что работа вообще завершена |

Synchronization ≠ Orchestration. Первое — «не порви общие данные». Второе — «договоритесь, кто кого ждёт и когда можно выходить».

### Orchestration на WaitGroup (пример из тура)

`main` не должен вернуться, пока две горутины не закончат. Передача данных не нужна — подходит `sync.WaitGroup`:

```go
var wg sync.WaitGroup
wg.Add(2)

go func() {
    lowercase()
    wg.Done()
}()
go func() {
    uppercase()
    wg.Done()
}()

wg.Wait()
```

`Add` — сколько ждать; `Done` — «я закончил» (−1); `Wait` блокируется, пока счётчик не станет 0. Возврат из `main` гасит программу «с крайней жестокостью» — без гарантий orchestration легко потерять работу.

Правила из тура:

- когда число горутин известно заранее — один `Add(n)`; в стриминге допустим `Add(1)` перед каждой;
- держи `Add` и `Done` **в прямой видимости** (не прячь WaitGroup глубоко в параметрах — меньше багов);
- забытый `Done` → deadlock (`all goroutines are asleep`);
- `Add` слишком большой → deadlock; слишком маленький → программа уйдёт дальше **без гарантии**, что работа доделана;
- порядок чередования букв/задач **не гарантирован**. Даже если 100 раз подряд один и тот же вывод — это вероятность, не контракт (другая версия Go / ОС / архитектура может вести себя иначе).

### Preemptive scheduler

Планировщик **вытесняющий**: нельзя предсказать момент context switch — и при каждом запуске картина другая. Это нормально: конкурентность должна оставаться *undefined out of order*.

На одном P (`GOMAXPROCS(1)`) горутины всё равно конкурентны (чередуются), но не параллельны. На двух P чередование становится мельче: вывод «перемешан» сильнее — это уже и concurrency, и parallelism.

На собесе: G/M/P; Running/Runnable/Waiting; sync vs orchestration; зачем WaitGroup в `main`; почему порядок горутин не контракт; что даёт `GOMAXPROCS`.

## Три обязанности автора concurrent-кода

По design guidelines Ultimate Go ты отвечаешь за:

1. **Startup / shutdown с integrity** — знать, когда каждая горутина умирает; уметь остановиться по требованию.
2. **Back pressure** — точки, где горутины ждут (каналы, mutex, atomic). Немного давления — нормальный баланс; много — дисбаланс, лавина отказов, «заморозка». Back pressure — сигнал о здоровье системы.
3. **Rate limit + timeouts** — не брать работы больше, чем можешь; отвергать новое рано; никакая задача не должна длиться вечно. Таймауты и отмена — через `context`: верхний уровень говорит нижнему, сколько времени есть.

Архитектура: замечать проблему → остановить кровотечение → вернуть систему в норму.

## Data race

**Data race** — две или больше горутин обращаются к одному ресурсу, и хотя бы одно обращение — **запись**, без синхронизации. Баги выглядят случайно или «никогда не проявляются» локально, а на проде портят данные.

Ловят так:

```bash
go run -race .
go test -race ./...
```

Race detector находит только то, что **реально выполнилось** — без покрытия тестами часть гонок останется невидимой.

Способы синхронизации доступа к shared state (когда каналы не упрощают задачу):

| Инструмент | Когда |
|------------|--------|
| `sync/atomic` | простые счётчики / флаги, узкий критический участок |
| `sync.Mutex` | эксклюзивный доступ к структуре / слайсу |
| `sync.RWMutex` | много читателей, редкие писатели |
| канал | оркестрация и сигналинг; «поделиться памятью через коммуникацию» |

Классика гонки — общий слайс/`map` + `append` из нескольких горутин без mutex. `map` без синхронизации при конкурентной записи — тоже race (и возможный panic).

Дополнительно Ultimate Go поднимает **false sharing** (ложное разделение в CPU-кэше): потоки пишут в разные переменные, но они лежат на одной cache line → лишний трафик когерентности, масштабирование «не едет». Если алгоритм не масштабируется — смотри раскладку данных в памяти, не только локи.

На собесе: определение data race; `-race`; mutex vs atomic vs канал; почему копировать `WaitGroup`/`Mutex` нельзя.

## Каналы: сигналинг, не «очередь»

Главный сдвиг мышления Ultimate Go: **не проектируй канал как очередь**. Канал — про **signaling semantics**: сообщить другой горутине событие (с данными или без) и упростить оркестрацию.

Вопрос гарантии доставки: *нужна ли гарантия, что сигнал, который я отправил, уже принят?*

### С данными vs без данных

Сигнал **с данными** — передаёшь значение (`ch <- v` / `v := <-ch`).  
Сигнал **без данных** — часто `chan struct{}` или закрытие канала: «хватит / отмена / deadline». Закрытие идеально как broadcast «стоп» всем читателям.

### Буфер и гарантия

| Вид | Порядок (по смыслу рандеву) | Гарантия | Цена |
|-----|------------------------------|----------|------|
| **Небуферизованный** | receive «раньше» send завершится вместе | 100%: сигнал принят | неизвестная задержка, пока не найдётся получатель |
| **Буферизованный** | send может завершиться до receive | чем больше буфер, тем слабее гарантия «уже приняли» | меньше блокировок между сигналами |
| **Буфер 1** | компромисс | «одна отложенная» гарантия | часто достаточно для continuity |
| **nil-канал** | send/receive блокируются навсегда | «выключить» ветку `select` | rate limit / временная пауза сигналинга |
| **close** | close до receive (как у buffered по смыслу сигнала) | сигнал без данных всем | только отправительская сторона закрывает |

Буфер **не для «ускорить» наугад**. Большой буфер маскирует back pressure (bufferbloat): ты поздно узнаёшь, что потребитель не успевает, растёт latency. Буфер — для измеренных всплесков и continuity handoff, не как безразмерная очередь.

Правило: если send **может** заблокировать отправителя — особенно осторожен с `cap > 1`, понимай, что будет при блокировке. Если send **не должен** блокировать — либо точный размер под fan-out (по слоту на send), либо drop-паттерн с измеренной ёмкостью.

Меньше буфера — чаще лучше. Фокус: сигналинг и оркестрация, не «поделиться стейтом через канал вместо mutex» без причины.

Состояния канала: `nil` / open / closed — поведение send/receive/close от состояния разное (закрытый + send → panic; receive из закрытого → zero value + `ok=false`).

```go
// небуферизованный: рандеву, гарантия доставки
ch := make(chan int)

// буфер под известный burst / fan-out
ch := make(chan int, n)

// отмена без данных
done := make(chan struct{})
close(done) // все <-done разблокируются
```

На собесе: unbuffered vs buffered и *guarantee of delivery*; зачем `chan struct{}`; кто закрывает канал; nil в `select`; почему большой буфер опасен.

## Context

Пакет `context` несёт **deadline, отмену и request-scoped values** через границы API и горутины. В Ultimate Go / stdlib-заметках:

- входящий запрос к серверу **создаёт** Context;
- исходящие вызовы **принимают** Context;
- цепочка вызовов **протаскивает** один и тот же ctx;
- дочерние: `WithCancel`, `WithDeadline`, `WithTimeout`, `WithValue`;
- отмена родителя отменяет детей;
- **не клади** Context в структуру «навсегда» — передавай первым аргументом `ctx context.Context`;
- **не передавай nil** — если неясно, что взять, `context.TODO()`;
- `Value` — только request-scoped данные (лакмус Sameer Ajmani: *могло бы это быть HTTP-заголовком?*); не для опциональных параметров функции;
- один Context безопасно использовать из многих горутин.

```go
ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
defer cancel()

select {
case res := <-work(ctx):
    fmt.Println(res)
case <-ctx.Done():
    fmt.Println(ctx.Err()) // Canceled или DeadlineExceeded
}
```

Функции, где пользователь ждёт ответа, должны уметь слушать `<-ctx.Done()`, когда иначе блокировались бы навсегда. Таймаут на Context ставь, когда у операции реальный time budget; решение «сколько ждать» — у caller’а выше по стеку.

Связь с каналами: `Done()` — это канал сигнала **без данных** (закрытие = отмена). Context — стандартизированная обёртка над этой идеей плюс дерево отмен и значения запроса.

На собесе: зачем Context в каждом RPC/DB-вызове; `Background` vs `TODO`; почему `defer cancel()`; Value не для DI.

## Как это стыкуется с паттернами

| Идея Ultimate Go | Паттерн / практика |
|------------------|-------------------|
| Оркестрация сигналами | pipeline, fan-out / fan-in |
| Ограничить параллелизм | worker pool, semaphore |
| Не блокировать send навсегда | drop, bounded buffer |
| Гасить работу | cancellation + `context` |
| Shared state | mutex / atomic, когда канал усложняет |

См. `patterns/theory.md`, `patterns/workerPool.go`, `patterns/pipeline.go`.
