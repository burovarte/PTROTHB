# PostgreSQL в Go-сервисе

PostgreSQL обычно хранит основную бизнес-информацию сервиса: пользователей, заказы, платежи и остатки товаров. База данных помогает не только сохранять данные, но и защищать их от некорректных состояний.

## Таблицы и ограничения

Таблица состоит из строк с одинаковыми колонками. Ограничения проверяются самой БД — приложение не сможет случайно сохранить данные, нарушающие правило.

```sql
CREATE TABLE orders (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id bigint NOT NULL REFERENCES users(id),
    status text NOT NULL CHECK (status IN ('new', 'paid', 'cancelled')),
    external_id text UNIQUE,
    created_at timestamptz NOT NULL DEFAULT now()
);
```

| Ограничение | Что гарантирует | Пример |
|---|---|---|
| `PRIMARY KEY` | Уникальный идентификатор строки, не `NULL` | `orders.id` |
| `FOREIGN KEY` | Ссылка ведёт на существующую строку | `orders.user_id → users.id` |
| `UNIQUE` | Значение не повторяется | внешний ID платежа |
| `CHECK` | Значение удовлетворяет условию | цена больше нуля |

`CHECK` подходит для правил одной строки. Связь между таблицами выражают через `FOREIGN KEY`.

Нюанс `NULL`: обычный `UNIQUE` допускает несколько `NULL`, а `CHECK` отклоняет только `false`, но не неизвестное значение. Для обязательного поля нужен отдельный `NOT NULL`. Таблица `users` в примере должна уже существовать.

## Что такое транзакция

**Транзакция** — группа SQL-операций, которая выполняется как единое целое: либо применяются все изменения, либо ни одно. Это защищает данные от частично выполненной операции.

Например, при переводе денег нельзя списать сумму у отправителя и не зачислить получателю:

```sql
BEGIN;

UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

COMMIT;
```

При ошибке выполняют `ROLLBACK`, и PostgreSQL отменяет изменения транзакции. Транзакции должны быть короткими: внутри не ждут HTTP-ответы, не отправляют письма и не выполняют долгую обработку.

Это иллюстрация атомарности, не готовый алгоритм перевода: приложение обязано проверить существование обоих счетов, достаточность средств и число изменённых строк. Успешный `UPDATE`, изменивший 0 строк, не вызывает автоматический rollback. Параллельные переводы также требуют защиты от конфликтов.

## Почему `sql.DB` — пул соединений

`sql.DB` в Go — это не одно постоянное соединение с PostgreSQL, а **пул соединений**: объект, который хранит несколько соединений, выдаёт свободное операции и возвращает его в пул после завершения запроса.

Несколько соединений нужны, потому что сервис обрабатывает запросы одновременно. Если бы было только одно соединение, пока один запрос ждёт БД, остальные вынужденно стояли бы в очереди. Пул позволяет выполнять запросы параллельно, переиспользовать уже созданные соединения и не перегружать PostgreSQL их бесконтрольным количеством.

```go
// Нужна регистрация драйвера:
// import _ "github.com/jackc/pgx/v5/stdlib"
db, err := sql.Open("pgx", dsn)
if err != nil {
    return err
}

db.SetMaxOpenConns(20)       // максимум соединений с БД
db.SetMaxIdleConns(10)       // сколько свободных держать готовыми
db.SetConnMaxLifetime(time.Hour)

pingCtx, cancel := context.WithTimeout(ctx, 2*time.Second)
defer cancel()
if err := db.PingContext(pingCtx); err != nil {
    db.Close()
    return err
}
```

Числа выше — пример, а не универсальные настройки. При завершении приложения вызывают `db.Close()`.

`sql.Open` обычно ещё не устанавливает соединение; доступность проверяет `PingContext`. Суммарный бюджет соединений считают по всем репликам: 10 экземпляров по 20 — уже до 200 соединений. `db.Stats()` помогает увидеть ожидание пула.

Транзакция `sql.Tx` удерживает одно соединение: внутри неё вызывают методы `tx`, а не `db`. Для выборки нескольких строк нужны `defer rows.Close()` и проверка `rows.Err()` после цикла; ошибку `QueryRowContext` получают при `Scan`.

## Таймауты запросов

На уровне Go задают дедлайн через `context`: он отменит запрос, если тот выполняется слишком долго.

```go
queryCtx, cancel := context.WithTimeout(ctx, 2*time.Second)
defer cancel()

err := db.QueryRowContext(
    queryCtx,
    `SELECT id, status FROM orders WHERE id = $1`, orderID,
).Scan(&order.ID, &order.Status)
```

Дополнительно на стороне PostgreSQL можно установить `statement_timeout`: БД сама остановит слишком долгий SQL-запрос. Обычно используют оба уровня.

Дедлайн Go включает ожидание свободного соединения. Отмена зависит от поддержки драйвером и не обещает мгновенной остановки. `lock_timeout` отдельно ограничивает ожидание блокировки. `SetConnMaxLifetime` — срок переиспользования соединения, **не таймаут SQL**.

## Миграции

**Миграция** — версионированное изменение схемы БД: создание таблицы, колонки, индекса или ограничения.

```text
001_create_users.up.sql
002_create_orders.up.sql
003_add_orders_status_index.up.sql
```

Миграции хранятся в Git и применяются по порядку. Уже применённую миграцию не редактируют: для следующего изменения добавляют новый файл. Благодаря версиям у разработчиков, тестового окружения и production получается одинаковая схема и понятная история её изменений.

При rolling update старый и новый код некоторое время работают вместе. Применяют **expand → migrate → contract**: сначала совместимое расширение схемы, затем перенос данных/кода, и только потом удаление старого. Проверяют время блокировок; `CREATE INDEX CONCURRENTLY` нельзя выполнять внутри обычного transaction block. Обратная миграция не всегда может восстановить удалённые данные.

## EXPLAIN и EXPLAIN ANALYZE

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 42;

EXPLAIN ANALYZE
SELECT * FROM orders WHERE user_id = 42;
```

- `EXPLAIN` показывает **план**, который PostgreSQL собирается выполнить: оценки количества строк и операций.
- `EXPLAIN ANALYZE` реально запускает запрос и показывает фактические время и количество строк.

Смотрят, насколько оценки отличаются от факта, и какие операции выбраны: например, `Seq Scan` — последовательное чтение таблицы, `Index Scan` — чтение через индекс. `Seq Scan` не всегда плох: для маленькой таблицы или чтения её большой части он может быть выгоднее индекса.

`EXPLAIN ANALYZE` для `UPDATE` или `DELETE` действительно меняет данные. Для проверки такого запроса используют транзакцию с `ROLLBACK`.

## Когда нужен SELECT FOR UPDATE

`SELECT FOR UPDATE` нужен в операции «прочитать → проверить → изменить», когда несколько запросов могут одновременно менять одну и ту же строку.

Например, при резервировании товара:

```sql
BEGIN;

SELECT quantity FROM products WHERE id = 10 FOR UPDATE;
-- Приложение проверяет, что строка найдена и quantity > 0.
-- Иначе ROLLBACK, а не переход к COMMIT.
UPDATE products SET quantity = quantity - 1
WHERE id = 10 AND quantity > 0
RETURNING quantity;

COMMIT;
```

Команда блокирует выбранную строку до `COMMIT` или `ROLLBACK`; конкурентное изменение этой строки будет ждать. Блокировку держат недолго, иначе растёт время ожидания и риск взаимной блокировки.

Во многих случаях проще применить одно атомарное обновление:

```sql
UPDATE products
SET quantity = quantity - 1
WHERE id = $1 AND quantity > 0
RETURNING quantity;
```

Если `RETURNING` не вернул строку, товар не найден или остатка не хватило. В Go это проверяют через `Scan` и `sql.ErrNoRows`; нельзя сообщать об успешном резервировании. Блокировка строки не блокирует обычное чтение её видимой версии и не защищает отсутствующую строку.

## Ещё три обязательных понятия

- **MVCC** — хранение версий строк: читатели видят снимок данных. В PostgreSQL `Read Committed` — стандартный уровень изоляции, новый снимок для каждого оператора; вся транзакция не обязательно видит одну картину.
- **Deadlock** — взаимное ожидание блокировок. PostgreSQL прерывает одну транзакцию; повторяют всю операцию с ограничением попыток. Единый порядок захвата строк снижает риск.
- **WAL** — журнал изменений для восстановления; **autovacuum** убирает ненужные версии строк и помогает поддерживать статистику. Это не замена backup.

Индексы, уровни изоляции и JOIN подробнее в [общем конспекте БД](<20. Базы данных.md>).

## Что важно на собеседовании

1. `sql.DB` — потокобезопасный пул, а не физическое соединение; его обычно создают один раз на всё приложение.
2. Таймаут запроса задают через `context` в Go, а `statement_timeout` служит защитой на стороне PostgreSQL.
3. Версионированные миграции дают одинаковую, воспроизводимую схему БД во всех окружениях.
4. `SELECT FOR UPDATE` применяют внутри короткой транзакции, когда нужно защитить read-modify-write от параллельного изменения.
5. `EXPLAIN` показывает оценки планировщика, `EXPLAIN ANALYZE` — реальные показатели после запуска запроса.
